# Decision — راستی‌آزمایی ادعاهای ریفکتور پیش از تغییر بات

## تصمیم و محدوده

بررسی روی شاخه main و پایه d09a4b4 انجام شد. در شروع، working tree تمیز بود.
فقط توضیح معماری و این گزارش تغییر کردند. .env، کد اجرایی، منابع، ترتیب
ترجمه، فرمت پیام و ماژول‌های Hermes تغییر نکردند. حذف و یکپارچه‌سازی بزرگ
بدون انتخاب کاربر انجام نشد. بررسی صفر قبل از اولین تغییر کامل شد.

  کم‌خوانی هدفمند AGENTS.md با ثبت و جست‌وجوی memory در CLAUDE.md سازگار است.

  نکرد. samemind recall با BM25 انجام شد؛ نبود نتیجهٔ handoff به معنی نبود

  CLAUDE.md به آنها ارجاع می‌دهد وجود ندارند. دستورها یا این ارجاع‌ها اصلاح نشدند.

الگوها فیلدهای خالی و placeholder دارند؛ Decision/Session واقعیِ بات در این
شش پوشه پیدا نشد. اما ledger/events.jsonl قالب نیست: دو رویداد واقعی samemind-health
در ۲۰۲۶-۰۸-۲۳ دارد، یکی fail و دیگری recovery/ok. .gitkeepهای fleet و ledger هم
توضیح کارکرد ابزار را دارند. پس گزارهٔ نبود محتوای واقعی بات در canon درست است،
اما ادعای انحصار فایل‌ها و خالی‌بودن کامل این ساختار رد می‌شود.

همچنین پیش از این گزارش، inbox/ ده markdown داشت: index و ۹ یادداشت واقعی
پروژه، از جمله Decision مربوط به FxEmbed و Session/Planهای لینک دستی.

مرحلهٔ الف اجرا نشد؛ دو انتخاب برای کاربر:
1. حفظ ساختار samemind و افزودن یک توضیح کوتاه دربارهٔ جدایی memory از بات.
2. حذف فقط scaffolding بلااستفاده پس از تصمیم دربارهٔ ادامهٔ استفاده از samemind؛
   حذف کل ledger یا inbox پیشنهاد نمی‌شود چون سابقهٔ واقعی دارند.
هیچ پوشه یا template حذف نشد.

AST هر ۱۰۳ فایل Python تحت Git بررسی شد: هیچ import یا from-import به

installer مسیر فایل را برای اجرای stdio به hermes mcp add می‌دهد.
lfc_mcp_server.py:285–306 حلقهٔ JSON-RPC روی stdin و ورودی مستقل __main__ دارد؛
docs/DECISIONS.md:21 کاربرد پل MCP برای Hermes را ثبت کرده است. پس این یک
entry point مستقل است، نه کتابخانه‌ای که باید از main import شود.

.mcp.json فعلی فقط samemind دارد؛ ثبت‌شدن واقعی سرور در تنظیمات Hermes این
ماشین بررسی یا ادعا نشد. هیچ تست در tests/ به نام lfc_mcp_server ارجاع ندارد؛
تست‌های AI/Hermes معادل تست مستقیم این سرور فرض نشدند.

مرحلهٔ ب اجرا نشد. حفظ سرور مستقل از وصل‌کردن حلقهٔ stdin آن به main منطقی‌تر
است. حذف قابلیت اختیاری هم فقط پس از تصمیم کاربر دربارهٔ Hermes قابل بررسی است.
هیچ ماژول یا تست مرتبطی حذف و هیچ مسیر Hermes فعال نشد.

## ادعای ۳ — رد شد به‌صورت کامل؛ بخش خرابی xscrape تأیید شد

دو مسیر هنوز وجود دارند: sources/twitter.py:983، _fetch_xscrape برای bulk؛
و :1210، item_from_url برای لینک دستی. dispatcher در :1227 شاخهٔ xscrape دارد.
اما لینک دستی در حالت fxembed از fxembed.fetch_tweet استفاده می‌کند.

اجرای واقعی روی لینک یکسان:
https://x.com/_pauljoyce/status/2103517340897771521

| حالت | HTTP و داده | خروجی item_from_url |
|---|---|---|
| fxembed | api.fxtwitter.com، 200، ۲۵۸۶ بایت، ۰٫۴ ثانیه | item معتبر، متن مصاحبهٔ کودی خاکپو |
| xscrape | x.com، 200، ۱۲۶۶۹۳ بایت، بدون relay، ۱٫۲ ثانیه | None |

این اجرا خرابی HTML این لینک در زمان بررسی را ثابت می‌کند؛ به معنی اثبات
خرابی تمام لینک‌ها برای همیشه نیست. برای این probe فقط درخواست عمومی HTTP
انجام شد؛ هیچ پیام واقعی به تلگرام ارسال و polling واقعی اجرا نشد.

شکست برای ادمین ساکت نیست: main.py:1058–1063 از قبل None را تشخیص می‌دهد و
«استخراج توییت ناموفق بود — حذف شده یا x.com بلاک کرد. دوباره امتحان کن.» می‌فرستد.
همین مسیر با fake Telegram و نتیجهٔ None اجرا شد و پیام فوق واقعاً ثبت شد.
پس تستی با فرض «هیچ پیام خطایی نیست» وضعیت فعلی را درست توصیف نمی‌کند؛ تست
FAIL ساختگی یا فیکسی برای باگِ از قبل رفع‌شده نوشته نشد.

همچنین inbox/2026-09-27-fxembed-twitter-source.md:47–48 و بخش fallbackها صریحاً
حفظ xscrape/classic را گفته‌اند، نه حذف کامل آنها. بنابراین عبارت «حذف طبق
Decision قبلی ناقص مانده» با متن همان Decision مخالف است.

مرحلهٔ ج اجرا نشد: xscrape حذف نشد، چون ادعای کامل رد شد و کاربر تغییر رفتار
منابع را جز با شرط تأیید منع کرده است. اگر حذف مسیر مرده را مستقل از این
ادعا انتخاب کند، باید dispatcher، تنظیمات و تست‌های bulk مربوط با هم بررسی شوند؛
کلیدهای _xscrape_media/_xscrape_quoted قرارداد مشترک FxEmbed هستند و نباید با
حذف transport به‌اشتباه پاک شوند.

## ادعای ۴ — تأیید شد، با اندازه و مرز دقیق

main.py برابر ۱۶۳۷ خط است. _process_item_internal از خط ۲۳۷ تا ۵۸۱، یعنی
۳۴۵ خط است؛ «حدود ۳۴۷» نزدیک است. article_pipeline.py دقیقاً ۶۴۷ خط دارد.
دو workflow وجود دارند، ولی polling یک خبر را از هر دو عبور نمی‌دهد:

1. main → poller_loop → run_cycle → collect/_fetch_source → ثبت SQLite و policy
   → انتخاب صف → process_item → _process_item_internal → پیش‌نمایش ادمین.
   تمام منابع فعال polling، از جمله RSS، باشگاه و Twitter، همین مسیر را دارند.
2. bot_loop → handle_message → _handle_tweet_link یا _handle_lfc_link
   → process_item(force=True). لینک دستی باشگاه وابسته به ENABLE_ARTICLES نیست.
3. bot_loop → handle_message → _handle_article_link → article_pipeline.run
   → process_article؛ فقط لینک دستیِ غیرتوییتر/غیرباشگاه وقتی ENABLE_ARTICLES=true.
   این مسیر archive/Wayback، استخراج مقالهٔ کامل، ترجمه، Telegraph و پیام لینک
   را انجام می‌دهد؛ article_cache دارد و وارد صف خبر و دکمهٔ تأیید پست نمی‌شود.
   همین فایل یک CLI مستقل نیز دارد.

handlerهای لینک می‌توانند در thread با polling هم‌زمان اجرا شوند. یک URL از
RSS و همان URL به‌عنوان مقالهٔ دستی ممکن است در دو فضای news و article_cache
وجود داشته باشد؛ اما فراخوانی خودکار دوگانه برای هر خبر مشاهده نشد.
ترجمه از قبل مشترک است: article_pipeline._translate در :442–445 فقط wrapper
async/thread برای translate.translate است. تولید پیش‌نمایش خبر با انتشار
مقالهٔ کامل در Telegraph یک خروجی واحد نیست.

مرحلهٔ د: توضیح این مرزها در docs/ARCHITECTURE.md افزوده و در a73a1f7 ثبت شد.
کد یکپارچه نشد؛ بازنویسی workflow یا ساخت wrapper تازه بدون تأیید کاربر انجام
نشد. وحدت بزرگ بدون تعریف یکسانِ cache/queue/output منطقی نیست.

## ادعای ۶ — رد شد به‌صورت بدون شرط؛ محیط تست تعیین‌کننده است
